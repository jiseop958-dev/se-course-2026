2. Transition. 시범 운영을 하기 위해선 그전에 이미 베타 배포가 가능한 제품이 완성되어 있어야 하기 때문. 즉, Construction 단계가 끝난 후여야 한다.
3. Inception. 이미 존재하는 게시판 시스템을 두고 새로 시스템을 개발할 필요가 있을까? 에 대한 논의를 하는 단계. 즉, Stop or Go를 정하는 단계
4. Construction. 최대 리스크를 이미 전 단계에서 처리한 후 나머지 유스케이스를 구현하는 단계이기 때문.
5. Construction. 신고 처리와 같은 기능들은 비교적 위험도가 낮고, 예측 가능한 범위이기 때문.
6. Inception. 핵심 유스케이스들을 식별하는 단계이기 때문.

EXERCISE 7-3
국면 - Inception 1주, Elaboration(I1~I2), Construction(I3~I4), Transition(I5), 총 11주

I1: 재학생 API 인증 요청 -> 응답 확인 -> 권한 승인 -> 적용 까지 구현하고 검증한다.
I2: 학생의 가입 신청을 동아리장이 승인하면, 신청 상태가 ‘승인’으로 변경되고 해당 학생이 동아리 회원으로 등록되는지 검증한다.
ㄴ 위험 요소: 인기 스터디/동아리 동시 신청으로 인한 정원 초과, 중복 가입 방지
I3: 사용자, 동아리/스터디의 유스케이스를 구현하고 검증한다.
I4: 관심 분야 및 선호 시간대에 따른 모임 매칭, 승인된 사용자끼리의 정보 공유 등의 편의 기능들을 구현하고 검증한다.
I5: 사용자를 대상으로 베타 테스트를 거쳐 개선사항을 수집, 재배포한다.

LCA 1: 재학생 인증 API가 실제로 연동되며, 인증 결과에 따라 서비스 이용 권한이 부여·적용되는 것이 확인되었다.
LCA 2: 스터디/동아리장의 승인에 따라 신청 상태가 변경되고 멤버로 등록되며, 동시 신청/승인과 반복 요청에도 정원 초과·동일 모임 중복 가입이 발생하지 않는 것이 확인되었다.
